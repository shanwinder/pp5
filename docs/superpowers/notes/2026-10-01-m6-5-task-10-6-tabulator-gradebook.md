## Bootstrap and progressive rendering

`GradebookController::show()` still obtains one authorized `GradebookReadService` model. `view.php` serializes only already authorized Gradebook presentation fields into a `type="application/json"` script using JSON hex escaping: offering ID, `canScore`, active component IDs/titles/maxima, enrollment IDs, student code/name, current/history status, nullable scores, and authoritative row summaries. It contains no national ID. No executable inline initialization is added. `gradebook.js` maps `enrollmentId` to Tabulator row `id`, and each score column to `score_<componentId>`. Visual coordinates locate cells only; each command re-resolves stable IDs. Sorting, filtering and column reordering are disabled.

The original semantic table and score/summary fragments remain. It is a readable fallback if Tabulator or initialization fails. While Tabulator builds, the fallback stays visible and the initializing grid stays visually hidden. Only after `tableBuilt` does the adapter disable fallback score inputs and hide the fallback, leaving one writable engine. The original HTMX single-cell fallback remains for an initialized page where Tabulator itself fails. A no-JS page retains the table and states that automatic saving requires JavaScript.

## Adapter state and write contracts

The adapter keeps explicit active cell, anchor/range, editor, composition, pending single/batch, revision, authoritative score, row revision, error, permission loss and uncertainty state. Tabulator's public row/cell/range APIs provide rendering and selection. Its native drag fill, range clear and clipboard paste mutation are disabled. The PP5 paste capture handler parses plain TSV, validates complete geometry, resolves stable IDs and submits one Task 8 batch command. The public `clipboardPasteAction` hook returns no native mutation. Delete and Backspace on a selected score rectangle, including **1×1**, use the same batch endpoint with explicit `""` fields. Ordinary editor commits use the existing single-cell endpoint. This avoids a blur-triggered duplicate and gives every selected clear the same atomic response contract. Explicit Task 9 fill uses the selected rectangle and a literal nonempty scalar through the batch endpoint; empty fill is refused in favor of clear.

The custom editor supports printable type-to-replace, Enter/F2 caret editing, ArrowUp/Down and Enter/Shift+Enter vertical commit/navigation, Tab/Shift+Tab horizontal commit/navigation and boundary exit, Left/Right caret movement, and Escape cancel without a write. Composition events and `isComposing` prevent premature keyboard commands. A single-cell response is confirmed only by HTTP 200 **and** `X-Gradebook-Saved: 1`; the adapter parses the existing score-cell and OOB row-summary fragments. A rejected value remains visible with error styling and `aria-invalid`; summaries retain prior authority. Batch confirmation requires HTTP 200 **and** `X-Gradebook-Batch-Saved: 1`, valid JSON, complete stable IDs and authoritative cells/rows. No client summary calculation is performed. Blank remains NULL at the server; `0`/`0.00` remain real scores.

Single requests are serialized in entry order, while rapid typing/navigation can continue across different cells. Operation revisions prevent older row summaries from overwriting newer ones. Programmatic cell/row application suppresses write handlers and retains scroll/selection where Tabulator permits. Paste, fill and clear reject while an editor or any single save is pending; a rejected range command is never queued or auto-retried. Transport loss, HTTP 200 without the marker, malformed confirmed response, HTTP 409 and server 5xx result in reload guidance and block further commands because commit status can be uncertain. A known validation rejection keeps values untouched and allows correction. Live permission revocation makes subsequent client editing ineligible; server authorization remains final.

Historical and read-only rows initialize in Tabulator for selection/copy but have no editor, paste, fill or clear authority. Mixed history, identity and summary rectangles reject the entire write at the UI boundary; Task 8 independently validates every target. Copy uses the selected visible rectangle as exact plain TSV, preserving empty fields and zero. Dynamic student/component text is escaped before Tabulator HTML formatting; server errors use text content.

## Task 10.6a — Cell editing visual correction

The product owner reported a second box/table appearance while editing. The isolated Chromium fixture reproduced a nested rectangle for click/type, Enter, and double-click editing. DOM inspection found one visible Tabulator grid, one editor input, and a hidden, disabled semantic fallback throughout. The extra rectangle came from the globally enforced `:focus-visible` outline on the input, layered over the active cell outline and range inset shadow. The PP5 input's negative margins also placed it beyond the cell edge. Its declared 2px border was overridden by Tabulator's editing-input rule in the measured browser, so that border was not the visible cause.

The PP5 theme now gives the editing cell the sole focus boundary, removes the input's border/outline/margins, and sizes the input inside the cell with border-box geometry. Editing suppresses the range inset shadow. A rejected active cell uses one dashed error boundary; rejected text remains visible. No adapter, fallback lifecycle, vendor, view, PHP business code, or server write contract changed.

Browser assertions cover one editor and hidden fallback during editing, borderless input geometry, stable row height/column width/internal scroll, cleanup after commit/cancel/rejection, responsive editing at 390/768/1024/1440 px, immediate editing after 3×3 clear, and over-max/nonnumeric rejection. ## Task 10.6b — Real keyboard and clipboard focus correction

The product owner reported that the production grid could lose Arrow, typing and clipboard interaction after normal pointer selection. In the isolated real Chromium fixture, clicking a score cell initially focused Tabulator's `.tabulator-tableholder` while PP5 marked the score cell active. A real 2×2 drag left DOM focus on the drag start but PP5 marked the bottom-right cell active; nine grid cells also retained `tabindex="0"`. This proves the focus-ownership and visual/keyboard mismatch. Arrow and type-to-edit still bubbled successfully from the holder in this isolated fixture, so the exact production failure frequency was not reproduced here. The normalized spike explicitly focused the selected cell after `cellClick`; production only called `activate(cell, false)`. The original browser helpers then called `target.focus()` after `target.click()`, concealing the missing production step.

Production now defers single-click focus until Tabulator finishes click selection. On mouse/pen pointerup it resolves the range's actual drag anchor and extent through public row/cell components, focuses the extent only after dragging ends, and leaves touch behavior alone. `activate` re-resolves the live cell by enrollment ID and component field, uses `preventScroll`, and scrolls only when the target is outside the grid viewport. `rowFormatter`, initial build, and render completion keep one active score cell at `tabindex="0"`; other rendered cells are `-1`, including newly virtualized rows. The active cell has one inset outline without a second range/focus shadow. No document-level keyboard/clipboard listener or hidden clipboard proxy was added.

Editor input retains focus during editing and composition. Existing caret Left/Right, vertical commit, Enter/Shift+Enter, Tab/Shift+Tab boundary exit, Escape, printable replacement and IME guards remain. Authoritative reconciliation re-resolves the active cell and restores focus only if the grid owned focus when applying the response and the user has not moved to an external control. A delayed-response browser test moves focus to the range input before the response and proves it stays there. Range paste starts from the active extent; reverse dragging makes the drag end the active extent. Writes still use enrollment/component IDs and existing Task 8/single-cell endpoints, with no backend, schema, permission, vendor or summary-authority changes.

The self-running browser scripts now click without calling `.focus()` on a score cell, wait for product code to establish focus, and assert one roving tab stop. Those scripts still dispatch synthetic keyboard/clipboard events for narrow command and payload checks; the external-focus test intentionally focuses an outside input to model leaving the grid. The 48-frame responsive matrix remains a geometry and editor-appearance check; real focus at each width was tested separately because concurrent iframes cannot all own browser focus.

Real in-app Chromium pointer/keyboard/clipboard verification on the isolated fixture covered click then Arrow, click then type, rapid `5 → Down → 6 → Down → 7`, forward/reverse 2×2 drag, Delete/Backspace, a real 3×3 drag/Delete, existing-value editor caret Left/Right and Backspace/Enter, Escape then Arrow, Tab boundary exit, real Cmd+V of `5\t0\n\t12.5`, and real Cmd+C yielding exactly `5.00\t0.00\n\t12.50`. The in-app browser clipboard API supplied/read the shortcut clipboard; this was browser-real in that environment, not an independently verified macOS system clipboard. The 2×2 request and 3×3 request geometry, blank versus zero, one batch request, stable IDs and authoritative responses were also checked by the fixture suites. Real click/Arrow passed at 390, 768, 1024 and 1440 px without document overflow. At 390 px, a far-right component retained internal horizontal scroll through typing, Arrow and paste; frozen identity stayed in place. After scrolling the 100×40 virtual grid to the end, a visible row still received click focus and Arrow navigation with one tab stop.

Focused browser results: writable 54 checks, read-only 12, race/keyboard 28, 2,001-cell limit 5, error matrix 18 scenarios, workload 35×20 15 and 100×40 8, responsive matrix 48 cases with no failures. ## Task 10.6d — Direct-entry arrow navigation

The product owner rejected Task 10.6c after finding that clicking a score, typing a number, and pressing ArrowLeft or ArrowRight kept the input open and moved its caret. The former canonical phrase “Inside the editor, Left/Right move the caret” failed to distinguish replacement typing from deliberately editing an existing value. Real pointer/keyboard actions in the isolated fixture reproduced that symptom before this correction: the editor held `5`, focus stayed on the input after Left/Right, and no single-cell request started; Up/Down already committed and moved.

The adapter now records `editIntent` as `direct` for printable typing and `explicit` for Enter/F2 or Tabulator's native double-click opening. Direct-entry Left/Right/Up/Down commit and move to writable score cells. An Arrow at a score or writable-row boundary commits and stays on the current cell; Tab retains grid exit at a horizontal boundary. Explicit-edit Left/Right remain native caret movement; its Up/Down, Enter and Tab commit and move. Both modes retain Escape cancellation, blur's single-commit guard, native input clipboard, composition protection, serialized single writes and stale-response reconciliation. The displayed Gradebook guidance and canonical contract explain the distinction. Backend endpoints, services, permissions and schema are unchanged.

The dedicated isolated fixture adds a third score component and `gradebook-direct-entry.js` covers direct and explicit openings, all four direct Arrows, rapid horizontal and vertical sequences with delayed responses, stable IDs, Arrow and Tab boundary behavior, Enter/Tab variants, Escape and native clipboard routing. It passed 53 synthetic checks. Separate real browser pointer/keyboard sequences confirmed horizontal `5 → 6 → 7`, vertical `5 ↓ 6 ↓ 7`, explicit double-click caret movement, Enter/F2 openings, native editor paste and multi-character `12.5 → ArrowRight`. The existing writable, read-only, parity, race, error, workload, responsive and cross-screen suites also passed after updating assertions that encoded pre-10.6d assumptions.

An authenticated Chrome MAMP session at `/gradebook/12` had one current student row. Reloaded HTML referenced `/assets/gradebook.js?v=1790922198`, matching the first-party file mtime, and displayed the revised guidance. A real click on its blank first score, typing `5`, then pressing Right saved `5.00` and focused the next score component. The score was cleared with the existing selected-cell Delete command; another reload confirmed the original blank and authoritative `6.00` row total were restored. Vertical movement on the actual MAMP page could not be tested with one row. Product-owner manual acceptance remains a separate gate.
