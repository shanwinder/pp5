## Interaction and authority

The writable page has a compact form immediately before the internally scrolling score matrix. It shows the current row, column, and cell count, a labelled text input with decimal input mode, an explicit fill button, and a separate clear button whose label includes the selected count. The form is hidden until Gradebook JavaScript initializes; read-only Gradebooks do not render it. The text input preserves the teacher's literal string: `0` is a real zero, `5.5` is sent literally and returns `5.50`, and malformed/hostile strings are sent literally for server rejection. Empty fill text stops locally with guidance to use clear. Clear constructs `""` for every field, never JSON null. Neither selection changes nor scalar typing sends a request. The scalar stays in the form during the page lifetime for another deliberate fill, without persistence or automatic repeat.

Only an explicit Task 7 selection can be a fill target. Every target is re-resolved from current score TD topology **at submission**. The client requires connected CURRENT score cells with editable inputs, rendered editability, matching offering/row/column/enrollment/component identities, consistent IDs across each row and column, and no duplicate enrollment or component IDs. A missing, disabled, historical, read-only, detached, malformed, or inconsistent cell rejects the entire selection. A historical or mixed historical/current rectangle remains selectable and copyable but has disabled write actions and explanatory text. The rendered Task 8 limit, currently 2,000 cells, disables/rejects larger selections. These are UI checks only; the batch service revalidates live permission, lifecycle, placement, ownership, maxima, and values.

Rows map top-to-bottom to `enrollment_ids`; columns map left-to-right to `component_ids`; each row-major `values` entry is the identical literal scalar or `""`. The action sends **one** POST to `/hx/gradebook/{offeringId}/scores/batch`. There is no fill/clear endpoint, fill service, alternate transaction, audit path, permission, or client total calculation. Mixed maxima stay separate; a scalar valid for a 20-point item but invalid for a 10-point item rejects the whole batch. Task 8 owns the one transaction, changed-cell audits, no-op detection, NULL versus zero, and authoritative row totals/completeness. A four-cell clear with two stored values, one retained NULL row, and one absent row changes and audits only the two stored values; it retains row identities and does not create the absent NULL row. Repeating canonical `5` over `5.00` changes and audits zero cells.

## Shared batch lifecycle and focus

Paste and fill/clear now use one `resolveEditableRectangle` and `submitBatch` path. The paste parser, focused-input start, TSV shape, blank/zero semantics, horizontal/historical spill rejection, and native paste interception stay intact. The shared command retains Task 8's `batchPending`, score-input freeze, pending single-cell guard, timeout, header/JSON/schema validation, all-DOM-before-apply validation, server response cell/summary updates, safe text feedback, aria-busy, and `batchValues` stale-blur suppression. No optimistic score value is shown. Success feedback names fill or clear and uses the server's targeted and changed counts. An authorized numeric error retains the scalar and selection, preserves displayed scores, and shows the server's student/item/max message. A confirmed commit with failed refresh, malformed response, timeout, network loss, or 200 without marker follows Task 8's conservative reload guidance; there is no automatic retry. Live revocation rejects without local changes. After success, the selected range remains visible, canonical values can be copied, and Task 6 navigation and Task 8 paste still work.

Focus inside the range action form belongs to the selection workflow. Focus on unrelated page controls still clears it. Moving an **unchanged** score input into the form suppresses an unnecessary blur POST; a dirty or failed input still enters Task 6's single-cell save, and fill waits for that save to settle before a deliberate retry. While a batch is pending, the fill/clear buttons are disabled and another fill, clear, or paste is not queued. Pointer dragging updates visual range silently until release; full writable-target validation is performed on completion and again at command time, rather than building matrices on every pointer move.

Keyboard path: focus a current score input, Shift+Down to extend a vertical range, Shift+Tab to the named grid region, then Shift+Tab through clear and fill buttons to the scalar field, type a value, and press Enter. Native Enter submits fill; an IME composition Enter is ignored. The clear button accepts native Enter/Space. Backspace/Delete remain input text editing and never clear a range. Shift+Left/Right remain native text selection. No drag-fill handle was added because Task 7 already owns drag selection; no formula, series, pattern, shortcut mode, or horizontal keyboard selection was introduced. The semantic table and native labelled controls remain; selection status is textual, pending/result feedback uses the existing polite region, and focus/selection have visible outlines. No screen-reader certification is claimed.
